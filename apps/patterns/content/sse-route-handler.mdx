## Problem

A page waits on server work that takes seconds and moves in steps. Polling is either slow (a long interval) or wasteful (a short one). A websocket is more than one-way updates need.

## Mechanism

A stream is one long HTTP response. The Route Handler returns a `Response` whose body is a `ReadableStream`, and keeps writing to it while the connection is open.

Each event is a frame of `field: value` lines ended by a blank line. The browser dispatches nothing until it sees that blank line, and `EventSource` fires a listener per `event:` name.

The browser remembers the last `id:` it received. When the connection drops, `EventSource` reconnects on its own and sends that id as the `Last-Event-ID` header, so the server can resume after it.

The stream ends with an explicit `done` event. A closed connection alone looks like a drop, and `EventSource` would reconnect. The client closes the source when it sees `done`.

While the server waits, it sends a `: ping` comment every 15 s. `EventSource` ignores comments; proxies and load balancers see traffic and do not close an idle connection.

The status line goes out as 200 before the first byte of work. A failure after that cannot change it, so errors travel as events.

Each open stream holds one function instance for as long as it is open. Keep the lifetime bounded, well under Vercel Fluid's 300 s limit.

`EventSource` covers a plain GET. When the request needs POST or custom headers, use `fetch` and read `response.body.getReader()` instead.

The producer polls or subscribes on the server. The browser never talks to the database.

### Resuming by hand

The demo passes `?lastEventId=` itself. `EventSource` sets `Last-Event-ID` only on its own automatic reconnects. A new `EventSource` created after `close()` starts with none, so the route reads the query param first and the header second.

## Pattern

The four files below are a working app. Paste them into a fresh Next project, open `/`, and watch the bar fill.

One event on the wire is three `field: value` lines and a blank line.

```text
id: 1
event: progress
data: {"percent":25,"step":"Checking dates"}

```

The blank line is part of the frame. The browser holds the three lines above it until that blank line arrives, then fires one `progress` listener with `event.data` set to the JSON text and `event.lastEventId` set to `1`.

The Route Handler writes those frames into a `ReadableStream` as the work moves on, and returns it with the three headers that keep the stream flowing.

```ts title="app/api/progress/route.ts"
const steps = [
  { id: 1, percent: 25, step: "Checking dates" },
  { id: 2, percent: 50, step: "Holding the room" },
  { id: 3, percent: 75, step: "Taking payment" },
  { id: 4, percent: 100, step: "Confirmed" },
];

function frame(event: string, data: unknown, id?: number) {
  const idLine = id === undefined ? "" : `id: ${id}\n`;
  return `${idLine}event: ${event}\ndata: ${JSON.stringify(data)}\n\n`;
}

export function GET(request: Request) {
  const lastEventId = Number(request.headers.get("Last-Event-ID") ?? 0);
  const pending = steps.filter((step) => step.id > lastEventId);
  const encoder = new TextEncoder();
  let timer: ReturnType<typeof setTimeout> | undefined;

  const stream = new ReadableStream({
    start(controller) {
      const send = (text: string) => controller.enqueue(encoder.encode(text));
      // The client left: stop the timer so nothing runs for nobody
      request.signal.addEventListener("abort", () => clearTimeout(timer), { once: true });

      const emit = (index: number) => {
        if (index === pending.length) {
          // The client closes on this; a bare close looks like a drop
          send(frame("done", {}));
          controller.close();
          return;
        }
        send(": ping\n\n");
        timer = setTimeout(() => {
          const { id, ...data } = pending[index];
          send(frame("progress", data, id));
          emit(index + 1);
        }, 1000);
      };
      emit(0);
    },
    cancel: () => clearTimeout(timer),
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      "X-Accel-Buffering": "no",
    },
  });
}
```

`steps` on a timer stands in for the server work. `Last-Event-ID` is the id the browser last saw, so a reconnect resumes after it instead of restarting. When `request.signal` aborts, the client has left: the timer stops, the loop ends, and no `done` goes out to nobody. `cancel` is the other way a client leaves, when the reader is dropped first. The `: ping` comment goes out before each wait; `EventSource` ignores a comment, and a proxy sees traffic on an idle connection. In real work, send one every 15 s while nothing happens. `no-transform` stops a compressing proxy from buffering the stream, and `X-Accel-Buffering: no` turns off nginx-style buffering in front of the function.

On the page, the `EventSource` lives in a small store module outside React. It opens on the first subscriber, closes when the last one leaves, and holds one snapshot object that it replaces on every event.

```ts title="app/progress-store.ts"
const initial = { percent: 0, step: "", status: "connecting" };

let snapshot = initial;
let source: EventSource | null = null;
const listeners = new Set<() => void>();

function update(patch: Partial<typeof initial>) {
  // A new object only when something changed; React compares snapshots with Object.is
  snapshot = { ...snapshot, ...patch };
  for (const listener of listeners) listener();
}

function open() {
  const events = new EventSource("/api/progress");

  events.addEventListener("progress", (event) => {
    const { percent, step } = JSON.parse(event.data);
    update({ percent, step, status: "running" });
  });
  events.addEventListener("done", () => {
    // Without this the browser would reconnect and run again
    events.close();
    update({ status: "done" });
  });
  events.addEventListener("error", () => {
    // CONNECTING means the browser is retrying with Last-Event-ID; only CLOSED means it gave up
    if (events.readyState === EventSource.CLOSED) update({ status: "failed" });
  });

  return events;
}

export function subscribe(listener: () => void) {
  listeners.add(listener);
  if (source === null) source = open();
  return () => {
    listeners.delete(listener);
    if (listeners.size === 0) {
      source?.close();
      source = null;
    }
  };
}

export function getSnapshot() {
  return snapshot;
}

export function getServerSnapshot() {
  return initial;
}
```

Every `progress` frame becomes one event with its `id` already remembered by the browser, and one new snapshot. `done` is where the store closes the source; without that call the browser would reconnect. An `error` fires on every drop, including the ones the browser recovers from by itself, so only `CLOSED` is a failure. The unsubscribe closes the source when the last component leaves, so a page the user left holds no connection. Between events `getSnapshot` returns the same object, which is what lets React skip renders.

The component reads that store with `useSyncExternalStore`.

```tsx title="app/ProgressView.tsx"
"use client";

import { useSyncExternalStore } from "react";
import { getServerSnapshot, getSnapshot, subscribe } from "./progress-store";

export function ProgressView() {
  const { percent, step, status } = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);

  return (
    <p>
      <progress value={percent} max={100} /> {percent}% {step} {status}
    </p>
  );
}
```

React calls `subscribe` when the component mounts and the returned function when it unmounts, so the component has no effect and no state of its own. That is the reason for the store: React owns the subscription lifecycle, every render reads one whole snapshot so `percent` and `status` can never come from different events, and there is no effect ordering to get right. The three functions and their rules are in [Reading an external store with useSyncExternalStore](/p/use-sync-external-store).

A page mounts the view.

```tsx title="app/page.tsx"
import { ProgressView } from "./ProgressView";

export default function Page() {
  return <ProgressView />;
}
```

The page is a Server Component and prerenders; only `ProgressView` runs in the browser, because of its `"use client"` line.

### Wrong and right

The run finishes, and the browser keeps reconnecting.

🔴 The server closed the connection without saying it was done. `EventSource` reads that as a drop, reconnects with `Last-Event-ID`, gets an empty run and a close, and repeats. This is the end of `emit` in the route above.

```ts title="app/api/progress/route.ts"
if (index === pending.length) {
  controller.close();
  return;
}
```

✅ Send a `done` event first, and close the source on the page when it arrives. The same lines in the route, and the `done` listener in the store.

```ts title="app/api/progress/route.ts"
if (index === pending.length) {
  send(frame("done", {}));
  controller.close();
  return;
}
```

```ts title="app/progress-store.ts"
events.addEventListener("done", () => {
  events.close();
  update({ status: "done" });
});
```

## Pitfalls

- **Every event arrives at once, when the stream ends.** A proxy is buffering the response. Send `X-Accel-Buffering: no` and `Cache-Control: no-cache, no-transform`, and do not compress the stream.
- **The page reports success on a run that failed.** The 200 went out before the work started, and a later failure cannot change it. Send the error as an event and let the page act on it.
- **The page stalls once a few tabs are open.** Browsers allow six HTTP/1.1 connections per origin, and each open stream holds one. HTTP/2 lifts the limit.
- **The function times out, or the bill grows with the number of visitors.** Every open stream is one function instance, billed for its duration. Bound the stream's lifetime.
- **Timers or subscriptions keep running after the tab is closed.** Nothing listened to `request.signal`. Stop the job on abort and in `cancel`.
- **`EventSource` reconnects forever after the stream ends.** There was no `done` event, so the close looked like a drop. See Wrong and right above.

## When not to use

- Upload progress. The browser already knows it: use `XMLHttpRequest.upload.onprogress`.
- Data that changes rarely. Poll or revalidate instead of holding a connection open.
- Anonymous, high-traffic pages. Each visitor holds a function instance.
