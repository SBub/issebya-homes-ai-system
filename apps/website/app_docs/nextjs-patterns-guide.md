# Next.js Patterns Guide

This guide covers Next.js patterns and conventions for this project.

---

## Database Operations in Route Files

When interacting with the database (fetching or creating data), place that logic in a route file (`route.ts`), not directly in page components.

### Why?

- Keeps data fetching logic centralized and reusable
- Separates concerns: routes handle data, components handle presentation
- Makes it easier to add caching, error handling, and validation in one place
- Allows multiple clients (pages, components) to use the same endpoint

### Example Structure

```
src/app/api/bookings/direct/route.ts   # GET bookings by session ID
src/app/(main)/booking/confirmation/page.tsx  # Uses fetch to call the API route
```

### Route File Example

```typescript
// src/app/api/bookings/direct/route.ts
import { NextRequest, NextResponse } from "next/server";
import { createClient } from "@issebya/shared/supabase";

export async function GET(request: NextRequest) {
  const sessionId = request.nextUrl.searchParams.get("session_id");

  if (!sessionId) {
    return NextResponse.json({ error: "session_id is required" }, { status: 400 });
  }

  const supabase = createClient();
  const { data, error } = await supabase
    .from("bookings_public")
    .select("*")
    .eq("stripe_session_id", sessionId)
    .single();

  if (error || !data) {
    return NextResponse.json({ error: "Not found" }, { status: 404 });
  }

  return NextResponse.json({ booking: data });
}
```

## Page Parameter Types

Use `PageProps` auto-generated by Next.js to type page component props. This provides type safety based on your actual route paths.

### Good - Use auto-generated PageProps

```typescript
// Next.js auto-generates PageProps types from your route paths
export default async function BookingPage(props: PageProps<"/booking/[type]">) {
  const { type } = await props.params;
  // ...
}
```

### Avoid - Manual inline types

```typescript
// Don't define manual types - use PageProps instead
export default async function BookingPage({ params }: { params: Promise<{ type: string }> }) {
  const { type } = await params;
  // ...
}
```

### Why PageProps?

- **Auto-generated**: Types are inferred from your actual route paths in `.next/types/`
- **Type-safe**: Parameter names match your `[param]` folder names exactly
- **Consistent**: Single pattern across all dynamic routes
- **Less boilerplate**: No need to define intermediate types

### Note

The `PageProps` type is globally available in Next.js 15+ with TypeScript. It's generated based on your app router file structure.

## Static Generation

Only use `generateStaticParams` when you actually need static generation for dynamic routes (e.g., blog posts, product pages with known IDs at build time).

### When to Use

- Pages with a finite, known set of dynamic values at build time
- SEO-critical pages that benefit from being pre-rendered
- Pages where data rarely changes

### When NOT to Use

- Pages with user-specific or session-specific content
- Pages with tokens, UUIDs, or unpredictable dynamic values
- Pages where data changes frequently

### Example: Remove Unnecessary generateStaticParams

If your page uses tokens or dynamic values that can't be known at build time:

```typescript
// DON'T add this - tokens are dynamic and unpredictable
export async function generateStaticParams() {
  return []; // Empty anyway, so remove it entirely
}
```

## Dependency Management

Only add packages to `package.json` when they are actually imported in code.

### Why?

- Avoids bloating `node_modules` with unused dependencies
- Prevents confusion about what the project actually uses
- Keeps bundle size accurate
- Makes dependency audits cleaner

### Rule: Import First, Install After

1. Write the code that imports the package
2. Then add the package to dependencies
3. Never add "planned" packages based on specs alone

### Bad: Adding packages preemptively

```bash
# Don't do this based on a spec saying "we'll use Popover"
yarn add @radix-ui/react-popover
# Then never actually import it
```

### Good: Add when actually used

```typescript
// First, write the code that uses it
import * as Popover from "@radix-ui/react-popover";

// Then install: yarn add @radix-ui/react-popover
```

### Before Committing

- Verify every new package in `package.json` has at least one import
- Run `grep -r "package-name" src/` to confirm usage

## Server Components by Default

Build pages as server components. Only use client components (`'use client'`) for genuine user interactions.

### Why?

- **SEO**: Server-rendered content is crawlable by search engines
- **Performance**: Less JavaScript shipped to browser
- **Simplicity**: No hydration, no client/server state sync issues

### Client Component Triggers

Only add `'use client'` when your component uses:

| Trigger                  | Example                            |
| ------------------------ | ---------------------------------- |
| React state hooks        | `useState`, `useReducer`           |
| Effect hooks             | `useEffect`, `useLayoutEffect`     |
| Browser APIs             | `window`, `document`, touch events |
| State-modifying handlers | `onClick={() => setState(...)}`    |

### Server Component Patterns

| Instead of...                | Use...                   |
| ---------------------------- | ------------------------ |
| `useState` for tab selection | URL params with `Link`   |
| `onClick` for navigation     | `Link` component         |
| Client-side data fetching    | `async` server component |
| `useEffect` for initial data | Server-side fetch        |

### Example: Tabs Without Client State

**Bad (client component):**

```tsx
"use client";
import { useState } from "react";

export default function Page() {
  const [activeTab, setActiveTab] = useState("tab1");
  return <button onClick={() => setActiveTab("tab2")}>Tab 2</button>;
}
```

**Good (server component with URL state):**

```tsx
import Link from "next/link";

export default async function Page({ params }: { params: Promise<{ tab: string }> }) {
  const { tab } = await params;
  return <Link href="/page/tab2">Tab 2</Link>;
}
```

### Component Audit Checklist

Before adding `'use client'`, ask:

1. Can I use `Link` instead of `onClick` for navigation?
2. Can I use URL params instead of `useState`?
3. Can I fetch data on the server instead of `useEffect`?
4. Is this interaction truly client-only (touch, animation, etc.)?

### Real Example: Booking Page

The `/booking/[type]/` page demonstrates this pattern:

- **Server components**: Page, Tabs (use `Link`), content blocks
- **Client component**: Gallery and availability calendar (touch/swipe, date pickers)

Result: Only interactive widgets ship JavaScript for client interaction.

## Tab Navigation: Use `<Link>` Not `<button>`

For tab-style navigation between pages, use `<Link>` instead of `<button>` with `router.push()`.

### Anti-Pattern: Button with router.push

```tsx
"use client";
import { useRouter } from "next/navigation";

function TabButton({ href, children }) {
  const router = useRouter();
  return <button onClick={() => router.push(href)}>{children}</button>;
}
```

Problems:

- Requires `'use client'` just for navigation
- No prefetching (worse performance)
- Not accessible (not recognized as a link)
- Middle-click doesn't open in new tab

### Correct Pattern: Link component

```tsx
"use client";
import Link from "next/link";

function TabLink({ href, isActive, onClick, children, className }) {
  return (
    <Link
      href={href}
      onClick={onClick} // For analytics tracking
      className={`${isActive ? "bg-[#d9b98b]" : "text-gray-600 hover:text-black"} ${className}`}
    >
      {children}
    </Link>
  );
}
```

Benefits:

- Automatic prefetching
- Proper accessibility semantics
- Standard link behaviors (right-click, middle-click)
- Still supports onClick for analytics

## Static Values at Module Scope

Move any value that doesn't depend on component state or props to module scope.

### Why?

- Avoids unnecessary re-creation on every render
- Communicates intent: "this is static configuration, not reactive"
- Slightly better performance (evaluated once at module load)

### Examples of What to Move Outside

| Move outside            | Keep inside               |
| ----------------------- | ------------------------- |
| Environment variables   | Values derived from props |
| Constant configurations | Values derived from state |
| Static style objects    | Computed/memoized values  |
| Regex patterns          | Context values            |
| Static arrays/maps      | Hook results              |

### Good - Module scope for static values

```typescript
const plausibleDomain = process.env.NEXT_PUBLIC_PLAUSIBLE_DOMAIN;
const DEFAULT_SETTINGS = { theme: 'light', locale: 'en' };
const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

export default function RootLayout({ children }: { children: ReactNode }) {
  // Component only contains reactive logic
  return <html>...</html>;
}
```

### Avoid - Static values inside component

```typescript
export default function RootLayout({ children }: { children: ReactNode }) {
  const plausibleDomain = process.env.NEXT_PUBLIC_PLAUSIBLE_DOMAIN; // Static - move out
  const settings = { theme: "light" }; // Static - move out
  // ...
}
```

## External Browser Subscriptions: Use `useSyncExternalStore`

When subscribing to browser APIs (scroll, resize, media queries, etc.), use `useSyncExternalStore` instead of `useEffect` + `addEventListener`.

### Why?

- **Concurrent-safe**: Works correctly with React 18 concurrent features
- **No tearing**: Prevents UI inconsistencies during concurrent renders
- **Server-safe**: Provides `getServerSnapshot` for SSR hydration
- **Cleaner separation**: Store logic is separate from component logic

### Anti-Pattern: useEffect + addEventListener

```tsx
// Avoid this pattern
"use client";
import { useEffect, useState } from "react";

function ScrollTracker() {
  const [scrollPercent, setScrollPercent] = useState(0);

  useEffect(() => {
    function handleScroll() {
      const percent =
        (window.scrollY / (document.documentElement.scrollHeight - window.innerHeight)) * 100;
      setScrollPercent(percent);
    }

    window.addEventListener("scroll", handleScroll);
    return () => window.removeEventListener("scroll", handleScroll);
  }, []);

  // ...
}
```

Problems:

- Can cause tearing with concurrent rendering
- Mixing subscription logic with component
- Manual cleanup management

### Correct Pattern: useSyncExternalStore

```tsx
"use client";
import { useSyncExternalStore } from "react";

function createScrollStore() {
  let cachedPercent = 0;

  function getScrollPercent(): number {
    if (typeof window === "undefined") return 0;
    const scrollableHeight = document.documentElement.scrollHeight - window.innerHeight;
    if (scrollableHeight <= 0) return 0;
    return (window.scrollY / scrollableHeight) * 100;
  }

  return {
    subscribe(callback: () => void): () => void {
      const handleScroll = () => {
        cachedPercent = getScrollPercent();
        callback();
      };
      window.addEventListener("scroll", handleScroll, { passive: true });
      return () => window.removeEventListener("scroll", handleScroll);
    },
    getSnapshot(): number {
      return cachedPercent;
    },
    getServerSnapshot(): number {
      return 0; // Default value for SSR
    },
  };
}

const scrollStore = createScrollStore();

function ScrollTracker() {
  const scrollPercent = useSyncExternalStore(
    scrollStore.subscribe,
    scrollStore.getSnapshot,
    scrollStore.getServerSnapshot,
  );

  // Use scrollPercent in effects or rendering
}
```

### When to Use

| Use `useSyncExternalStore` for | Keep `useEffect` for             |
| ------------------------------ | -------------------------------- |
| Scroll position                | One-time setup (analytics init)  |
| Window resize / dimensions     | DOM manipulation after render    |
| Media query changes            | Non-subscription side effects    |
| Online/offline status          | Timeouts and intervals           |
| localStorage changes           | Fetch requests (use React Query) |

### Performance Tip: requestAnimationFrame

For high-frequency events like scroll, throttle updates with `requestAnimationFrame`:

```tsx
subscribe(callback: () => void): () => void {
  let rafId: number | null = null;
  let ticking = false;

  function handleScroll() {
    if (!ticking) {
      rafId = window.requestAnimationFrame(() => {
        cachedPercent = getScrollPercent();
        callback();
        ticking = false;
      });
      ticking = true;
    }
  }

  window.addEventListener('scroll', handleScroll, { passive: true });
  return () => {
    window.removeEventListener('scroll', handleScroll);
    if (rafId !== null) window.cancelAnimationFrame(rafId);
  };
}
```

## Metadata: Use Export Instead of Inline Tags

Use the `Metadata` export API instead of inline `<meta>` tags in the `<head>`. This is Next.js's recommended pattern for managing page metadata.

### Why?

- **Type safety**: TypeScript validates metadata structure
- **Automatic handling**: Next.js handles deduplication and ordering
- **Cleaner JSX**: Keeps the component body focused on layout, not configuration
- **Better DX**: IDE autocomplete for all metadata properties

### Anti-Pattern: Inline Meta Tags

```tsx
// Avoid this pattern
export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <head>
        <meta property="og:title" content="Site Title" />
        <meta property="og:description" content="Description..." />
        <meta property="og:image" content="https://example.com/image.webp" />
        <meta property="og:url" content="https://example.com" />
        <meta property="og:type" content="website" />
        <meta name="twitter:card" content="summary_large_image" />
        <meta name="twitter:title" content="Site Title" />
        <meta name="twitter:description" content="Description..." />
        <meta name="twitter:image" content="https://example.com/image.webp" />
      </head>
      <body>{children}</body>
    </html>
  );
}
```

### Correct Pattern: Metadata Export

```tsx
import { Metadata } from "next";

export const metadata: Metadata = {
  title: "Site Title",
  description: "Description...",
  openGraph: {
    title: "Site Title",
    description: "Description...",
    url: "https://example.com",
    type: "website",
    images: [
      {
        url: "https://example.com/image.webp",
        alt: "Site Title",
      },
    ],
  },
  twitter: {
    card: "summary_large_image",
    title: "Site Title",
    description: "Description...",
    images: ["https://example.com/image.webp"],
  },
};

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <head>{/* Only non-metadata elements like scripts */}</head>
      <body>{children}</body>
    </html>
  );
}
```

### Dynamic Metadata

For pages with dynamic metadata (based on params), use `generateMetadata`:

```tsx
import { Metadata } from "next";

export async function generateMetadata(props: PageProps<"/blog/[slug]">): Promise<Metadata> {
  const { slug } = await props.params;
  const post = await getPost(slug);

  return {
    title: post.title,
    description: post.excerpt,
    openGraph: {
      title: post.title,
      description: post.excerpt,
      images: [{ url: post.image }],
    },
  };
}
```

## Summary

| Pattern               | Guideline                                                           |
| --------------------- | ------------------------------------------------------------------- |
| Database operations   | Place in `route.ts` files, not page components                      |
| Page params           | Use auto-generated `PageProps<'/route-path'>` type                  |
| generateStaticParams  | Only use for truly static, predictable routes                       |
| Dependencies          | Only add packages when actually imported in code                    |
| Server components     | Default to server; only use `'use client'` for genuine interactions |
| Tab navigation        | Use `<Link>` instead of `<button>` with `router.push()`             |
| Static values         | Move to module scope if no dependency on props/state                |
| Browser subscriptions | Use `useSyncExternalStore` for scroll, resize, media queries        |
| Metadata              | Use `Metadata` export instead of inline `<meta>` tags               |
