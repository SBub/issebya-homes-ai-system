# Design System: issebya.homes

## Overview

**Creative North Star: "The Guest House's Two Rooms"** (draft, proposed this pass — not yet confirmed with the user)

This site runs two honest, deliberately separate registers, not one unified skin forced over both. The **catalog register** (shop, blog, contact, and now `/booking/[type]`'s own page shell) is a flat, cream-on-gray boutique-catalog grammar: uppercase letter-spaced kickers, square photography, no handwritten type, no shadows. Roman-numeral position markers were a **shop-only** device within this register for most of this session (blog and contact never had them); shop's own numerals were removed in a later round, by explicit instruction, so no catalog-register surface uses them now — see Components below for the current, numeral-free `ProductCard`. The **host register** (the shared booking engine wherever it's embedded, plus guest-info, checkin, confirmation) is warmer and more personal: a beige ground, the handwritten "Nothing You Could Do" face for headlines and the site wordmark, bordered form controls, no roman numerals, no uppercase kickers. Both are load-bearing parts of the same real, shipped site — the catalog eye is what shop, blog, contact and booking's own shell use to present objects, stories, the host's own reachability and (now) the room itself; the handwritten voice is what carries the host's own personal, WhatsApp-only, non-corporate positioning through guest-info/checkin/confirmation and, unchanged, through the booking engine's own controls. Neither register is a mistake to be merged away.

The blog was rebuilt this session to mirror the shop's catalog grammar (same CSS custom properties, same card ground/kicker/title tokens, same hover-only title underline) rather than invent its own, then deliberately diverged in one specific, user-directed way at the time: no roman numerals on `PostCard`, while `ProductCard` still had them (a post isn't a numbered catalog item the way a product is). That divergence confirmed the catalog register as a real, reused system with room for a surface to depart from it on purpose, not a literal find-and-replace skin — and it turned out to anticipate the site's later direction: shop's own numerals were removed in a subsequent round, so `PostCard`'s numeral-free card is now simply what every catalog card looks like, not an exception to a rule `ProductCard` still follows.

One narrow, deliberate register crossover: the blog's inline `<BookingWidget>` (a host-register booking engine — calendar, dates, price, forms, identical to the one on `/booking`) sits inside a catalog-register wrapper (`bg-shop-card` panel, uppercase kicker "Book Your Stay") when embedded in a post, because the post around it is catalog-register. Only the wrapper crossed over; the booking engine's own internals were deliberately left on the host register's styling to avoid touching the shared component the main booking page also renders. See Components below.

`/contact` moved into the catalog register this session. It previously belonged to neither register — an unstyled photo, a plain paragraph, and a generic dashed-border `<Callout>` on the default white page background — which made it read as an unfinished page rather than a deliberate choice. It now mirrors shop/blog's own detail-page grammar (`bg-shop-card` panel, edge-to-edge, no `bg-shop-ground` wrapper) rather than their index-grid grammar, because contact is a single standalone surface, not a list of many items. The `<Callout>` component was left untouched (it's shared with `/booking/[type]`'s own usage, see below) and simply dropped from this page; its dashed-white-box styling had no catalog-register precedent, and the WhatsApp link now sits in the panel's own flowing body copy instead, using the existing `text-secondary-link-bold` treatment. See Layout and Components below for the specifics.

`/booking/[type]`'s own outer shell moved into the catalog register this session too, following the wrapper pattern the Inline Booking Widget had already established: the page's own background and footer copy now speak the catalog grammar, while the embedded booking engine — calendar, date buttons, price, forms — was left completely untouched on host-register styling at first, because it's the exact same shared `BookingEngine`/`BookingClient` component the blog's widget already wraps this way; restyling it here would have restyled that widget too (that reasoning was later deliberately reversed for color specifically — see Pure White under Colors). Concretely: the page's background is now `bg-shop-card` (previously the beige `--background`, supplied by a shared `booking/layout.tsx` that has since been removed); and the closing WhatsApp line dropped the dashed `<Callout>` for a plain `text-secondary` paragraph, exactly like `/contact` did. The room title (`Private room 1` / `Private room 2 with shared spaces`) first moved from the handwritten `text-header` to `text-price`, then was removed from the page entirely in a later round, by explicit user instruction ("i really don't like the title style") — see Typography > Hierarchy and Booking Page Shell below for the current state. `/booking/confirmation` — still host register, out of scope for this change — used to get its beige/flex-row page shell for free from that same shared `booking/layout.tsx`; it now carries an identical wrapper in its own `booking/confirmation/layout.tsx` so its appearance is unchanged. No Breadcrumb here either, for the same reason `/contact` has none: `/booking` has no listing page of its own (`booking/page.tsx` only redirects to room1), so this isn't a "listing › item" surface. See Layout and Components below for the specifics.

**Key Characteristics:**

- Two active registers, not one: catalog (shop, blog, contact, booking's own shell) vs. host (the booking engine itself, guest-info, checkin, confirmation).
- Flat surfaces everywhere; no shadow vocabulary in either register.
- Square corners throughout (`rounded: none`); no rounded-corner cards, buttons, or inputs found anywhere in the codebase.
- Real photography only, no illustration or iconography beyond a single inline heart glyph on the wishlist trigger.
- Work Sans is the only body/UI typeface; the handwritten face is reserved strictly for the host register's headlines and wordmark.

## Colors

The palette is warm and desaturated in both registers — gray-and-cream in the catalog, beige-and-black in the host register — with exactly one deliberately muted accent (below), no bright/saturated color anywhere else in the build.

### Primary

- **Catalog Cream** (`#f1eac8`, token `--color-shop-card`): the card and content-panel background for every shop and blog surface (`ProductCard`, `PostCard`, shop/blog detail-page split, the wishlist dialog panel, the Inline Booking Widget).
- **Catalog Ground** (`#6f6f6f`, token `--color-shop-ground`): the section background the cream cards sit on, used only on `/shop` and `/blog` index grids.
- **Pure White** (`#ffffff`, no custom token — Tailwind's core `bg-white`): `Header.tsx` and `Footer.tsx`'s own background, and the booking engine's outer surfaces (`.booking-date-button`, `.booking-engine-expanded`, the Close button) wherever the engine is embedded. White was already the color of the engine's own form inputs (name/email/phone/select, `.booking-person-button`) before this session; this extends it to the surfaces around them so the whole engine reads as one consistent white object instead of white inputs on a beige panel. By explicit user instruction — this is a deliberate exception to "the embedded component's internals stay untouched" (see the Inline Booking Widget and Booking Page Shell notes below): the engine's own color changed here, on purpose, everywhere it's embedded, not just on the canonical page.

### Secondary

- **Host Beige** (`#f0eeea`, root `--background`): the page background for guest-info, checkin, confirmation, and every other non-catalog page; also the fill on `.button-outline`'s other consumer (the shop wishlist trigger — the booking engine's own Close button no longer shares this fill, see Pure White above and Components below).
- **Tab Tan** (`#d9b98b`, inline arbitrary value, no named token): the active-tab fill for Room 1/Room 2, shared by `/booking/[type]` and the blog's Inline Booking Widget (both consume the same `tabStateClasses` helper). A muted terracotta (`#b5623f`) was tried and shipped briefly this session as a more legible alternative, then reverted back to this original tan by explicit user decision — treat the tan as the confirmed, standing choice, not a placeholder.

### Neutral

- **Ink** (`#000000`, root `--foreground`): all body text, all borders (`border-foreground`), and the fill on solid/active states (selected calendar day, primary booking buttons, filled wishlist heart).
- **Gray family** (Tailwind `gray-100`–`gray-600`, e.g. `#f3f4f6`, `#9ca3af`, `#4b5563`): disabled/blocked calendar days, helper text. No custom token; used directly as Tailwind grays. Breadcrumb trail text used to be `gray-600`; changed to plain black by explicit instruction — see Navigation under Components.

### Named Rules

**The Two-Register Rule.** A page belongs to the catalog register (shop, blog, contact, `/booking/[type]`'s own shell: `bg-shop-ground`/`bg-shop-card`, uppercase kickers) or the host register (guest-info, checkin, confirmation: beige `--background`, handwritten headline, bordered controls) — never a blend of both. Decide which register a new page belongs to before choosing its tokens. The one sanctioned exception is a catalog-register _wrapper_ around an unmodified host-register _component_ embedded inside it — the shared booking engine, wrapped this way both by the blog's Inline Booking Widget and now by `/booking/[type]`'s own shell — where the wrapper crosses over but the embedded component does not.

**The No-Bright-Accent Rule.** Neither register has a saturated accent color. Contrast and hierarchy come from cream/gray/beige/black value shifts, not hue — the Tab Tan above is a muted, desaturated fill, not an exception to this. Don't introduce a brand accent color without confirming it against both registers; one alternative (a terracotta) was already tried and explicitly declined this session.

## Typography

**Display Font (host register only):** Nothing You Could Do (handwritten, `--font-hand`), with a cursive fallback.
**Body Font (both registers):** Work Sans (`--font-work`/`font-sans`), with `ui-sans-serif, system-ui` fallback.

**Character:** Work Sans carries nearly everything — small, quiet, letter-spaced labels and plain-weight body copy. The handwritten face appears in exactly one role, the host register's headline/wordmark, giving it outsized, deliberate weight precisely because it is rare.

### Hierarchy

- **Host Headline** (bold, `text-xl`–`3xl` depending on context, `font-hand`): the site wordmark in `Header.tsx` and headline treatments on guest-info/checkin/confirmation. `/booking/[type]`'s own room title moved off this treatment onto `text-price` earlier this session, then was removed from the page entirely in a later round (see Catalog Title below); the booking engine's own copy never used it in the first place. Never used in the catalog register.
- **Catalog Title** (bold, `text-xl`, `text-price` utility): product names on `ProductCard` and blog post detail titles (`/blog/[slug]`'s `h1`). `PostCard`'s own listing-card title diverges by explicit instruction: `font-medium text-sm my-[10px]`, smaller and lighter than `text-price`, not the shared token — this is a deliberate departure from the earlier "match shop's title weight exactly" direction, the one place the two blog surfaces' title styling no longer agree with each other. The hover-only underline behavior is unchanged and still matches `ProductCard` exactly (`group-hover:underline underline-offset-4`) regardless of weight/size. Detail-page titles are NOT underlined in either register — a detail page you're already on gets no click affordance. Blog briefly shipped a permanent, always-visible underline on both blog surfaces earlier this session; reverted by explicit user decision back to hover-only. `/contact` briefly followed the same `text-price`-on-`h2` pattern for its own "Contact" title — a site-wide rule (`index-pages-no-title-heading.browser.test.tsx`) reserves the page's one `h1` for the header's site name on every nav-level page (`/blog`, `/shop`, `/contact`), so a page-title heading on one of these has to be an `h2`, precedented by `InfoSection`'s own `titleClassName="text-price"` sections on `/guest-info` — then had that title removed entirely in a later round, by explicit instruction, alongside its supporting photo; see Layout above for the current text-only state. Shop and blog's `text-price` `h1`s are on detail pages naming a specific item (a product, a post), which is a different case this rule doesn't touch and which those titles still use. `/booking/[type]` briefly followed the same `text-price`-on-`h2` pattern for its own room title (`Private room 1`/`Private room 2 with shared spaces`), then had that title removed from the page entirely in a later round, by explicit instruction ("i really don't like the title style 'private room', remove it for both room 1 & 2") — the room content column now goes straight from the tab bar into the collapsed booking engine, with no page-owned heading between them at all. The room identity is still available via the active tab label ("Room 1"/"Room 2") and the document `<title>` (`generateMetadata` still reads `ROOM_CONTENT[type].title`, unchanged — only the rendered `<h2>` is gone).
- **Prose Heading** (bold Work Sans, `text-xl`–`4xl`, tight top margin): in-article MDX headings (`mdx-components.tsx`), explicitly not the handwritten face, "so in-article headings stay bold Work Sans like the rest of the shop-mirrored surface."
- **Body** (`text-sm`, `leading-relaxed`, `text-secondary` utility): all card descriptions, MDX paragraphs, form labels, calendar and booking copy. Shop's product detail prose caps at `max-w-[65ch]`; blog's post detail prose deliberately does NOT cap its measure — it flows the full width of the `bg-shop-card` panel, by explicit user decision, after an earlier `max-w-[65ch]` constraint on that container left a large unused gap on wide viewports instead of using the panel's actual width.
- **Catalog Kicker** (`text-[10px]`–`text-xs`, `uppercase`, `tracking-[0.2em]`): brand name on `ProductCard`, formatted date on `PostCard` and blog detail, product/post detail brand line, wishlist dialog heading and buttons. Confined to the catalog register and the wishlist dialog it shares tokens with; never appears in the host register. Alignment diverges between the two catalog cards: `ProductCard`'s kicker is centered (matches its centered portrait layout); `PostCard`'s date kicker is left-aligned, by explicit instruction, matching the flush-left rhythm of the rest of its horizontal row.
- **Gallery Caption** (`text-xs`, `uppercase`, no `tracking` widening): the per-photo label under `/booking/[type]`'s main gallery image (`Gallery.tsx`), e.g. "GUEST BED - QUEEN SIZE (FLOOR 0)". Small and uppercase like the Catalog Kicker above, but a deliberately separate treatment, not a reuse of that token: `Gallery` lives inside the booking engine's own content column, which is host register (see Booking Page Shell below), and Catalog Kicker is explicitly confined to the catalog register. Briefly carried `font-medium` too, matching Booking Price below; dropped in a later round, by explicit instruction, so it's now plain weight — the two no longer share that trait, only the size/uppercase. No `tracking-[0.2em]` letter-spacing either. Don't collapse this into Catalog Kicker later without confirming that's wanted; they're two devices with a family resemblance, not one token used twice. The label's underlying text (`src/utils/images.ts`) stays normal mixed case; the caps are a CSS `text-transform`, not stored data.
- **Booking Price** (`.booking-price-per-night`, `text-sm`, `font-medium`, `uppercase`): the "75€ / NIGHT" line inside `BookingPricing.tsx`, shared by `/booking/[type]` and the blog's Inline Booking Widget. Used to be `text-price` (bold `text-xl`, matching the room title it sat under); dropped to this smaller, quieter treatment in the same round that removed the room title entirely, by explicit instruction — with no title above it demanding a large answer below, the price no longer needed to carry that weight. Shared `font-medium`/`uppercase` with Gallery Caption above when both were written in the same round, a coincidence of taste rather than a shared token even then; Gallery Caption has since dropped `font-medium` in a later round while this one kept it, so they've since drifted further apart, not closer.

### Named Rules

**The Handwritten-Is-Rare Rule.** `font-hand` renders only the site wordmark and host-register headlines. Every other heading in the codebase, including in-article MDX headings, is bold Work Sans. Don't reach for the handwritten face for card titles, kickers, or body copy in either register.

## Layout

**Every catalog-register page carries its own `min-h-screen`.** The shared `(main)/layout.tsx` renders `<Header /><main className="flex-1">{children}</main><Footer />` inside a `min-h-screen flex flex-col` root (`layout.tsx`) — a sticky-footer pattern where `<main>` stretches to fill any leftover viewport height on a short page. That stretch happens on `<main>` itself, which has no background; a page's own content div/section only grows to fit its content, so on a page shorter than the viewport (`/contact` reliably; `/shop`, `/blog` and their detail pages whenever the catalog is small or the viewport is tall) the leftover space inside `<main>` shows through as the root's plain Host Beige, a mismatched seam between the catalog-register color block and the footer. Every catalog-register page's own color-bearing element (the `bg-shop-card` panel on `/contact`, `/shop/[slug]`, `/blog/[slug]`, or the `bg-shop-ground` section on `/shop` and `/blog`'s index) now carries `min-h-screen` itself, so _that_ element's own background — not `<main>`'s — fills the leftover space and reaches the footer with no color break. This is a no-op on any page whose natural content already exceeds the viewport (the common case for `/shop` and `/blog` today); it only engages when content is short. `/booking/[type]`'s own page shell and `/booking/confirmation/layout.tsx` already carried `min-h-screen` for the same reason before this fix landed elsewhere. Host-register pages without a colored panel of their own (`/guest-info`, `/privacy-policy`, `/terms-and-conditions`) don't need this: their content sits directly on the root's own Host Beige, so there's no second color to seam against regardless of how short the page is.

**`Footer.tsx` and `Header.tsx` never try to match the register above/below them — they're their own third, explicitly white surface, marked off with a border.** The `min-h-screen` fix above closes the _gap_ before the footer; it does nothing about the footer _itself_. `Footer.tsx` and `Header.tsx` are each a single component shared by every page in `(main)/layout.tsx`/`layout.tsx` — originally both were unstyled and transparent, showing through to the root's plain Host Beige regardless of which register the page above/below belonged to, which on a catalog-register page was a hard, real color break that read as a "white/washed-out footer" once the `min-h-screen` fix had already closed the empty-space gap around it. Making Footer register-aware (a prop, or reading the route) was considered and rejected: Footer has exactly one call site, so it's not infeasible, but the color that would need matching isn't even uniform within the catalog register itself — `/shop`'s index has a plain-beige "Offer it here" line between its `bg-shop-ground` section and the footer already, so "match whatever's directly above" has no single answer to wire up. The settled fix, by explicit user instruction: both are `bg-white` (Pure White, see Colors above — a third color, not either register's own), marked off from the page with a hairline `border-gray-300` rather than a color match — `border-t` on Footer, `md:border-b` on Header. Footer's own internal padding also collapsed this same round: `border-t border-gray-300 py-3` with its four pieces (icon, two legal links, copyright) in one `flex flex-row flex-wrap` row instead of the three stacked rows and `pt-6 pb-4` it used to carry — a smaller footer, not just a recolored one. The border is what turns the white-vs-register color change from "a chunk of the page is missing" into "the footer/header starts here," the same way a footer sitting in a different color from the page body is completely normal elsewhere on the web as long as it reads as an intentional boundary. Unlike Header, which only borders on `md:`, Footer borders at every breakpoint — the seam is exactly as visible on mobile as on desktop, so the fix has to hold there too.

Both registers share one spacing rhythm: `px-4`/`py-10` on mobile stepping up to `px-12`/`py-16` on `md:`. The two catalog listings diverge deliberately: shop (`ProductCard`) runs a `grid-cols-1` → `sm:grid-cols-2` → `md:grid-cols-3` grid of portrait cards (`3/5` aspect ratio, relaxing to a `min-h-[26rem]` auto-height band in the cramped `md`-only three-column range, 768–1023px); blog (`PostCard`) is a single-column stacked list (`flex flex-col gap-6 max-w-3xl mx-auto`) of horizontal rows instead — no grid, see Components below. Neither card carries a roman-numeral position marker any more — see Position-Marked Catalog Card under Components for the current state and its history. Detail pages also diverge: shop's `/shop/[slug]` keeps a `grid md:grid-cols-2 gap-8` split (image one side, content the other); blog's `/blog/[slug]` instead floats its hero image (`float-left`, `w-2/5` on `sm:` and up, full-width stacked above the text on mobile) within an unconstrained `flow-root` prose container — no `max-w`, unlike shop's — so body text wraps around the image and flows at the full panel width once it clears, avoiding both the dead space a fixed-height grid column left when the image and text ran to different heights, and the dead space a narrower prose measure left unused on wide viewports. Both detail pages share the same `bg-shop-card` panel and a `Breadcrumb` component, rendered as that panel's own first child (not a separate wrapper above it — see Navigation under Components). `/contact` shares the same edge-to-edge `bg-shop-card` panel too, but carries neither a grid split, a floated hero, a title, nor a photo of its own any more: both its `text-price` `h2` ("Contact") and its `page-decor-photo` (the front-yard image, the same utility `/guest-info` uses for its own supporting photos) were removed by explicit instruction in a later round, leaving just a `max-w-[70ch]` block of `text-secondary` paragraphs — the page is now text-only. No `Breadcrumb` either: that component marks a "listing › item" trail, and contact isn't a child of `/shop` or `/blog`'s listings — it's a standalone nav destination, structurally closer to `/booking/[type]` or `/guest-info` than to a catalog detail page, even though it still borrows the catalog detail page's panel background. `/booking/[type]` itself now shares that same reasoning for the same reason (no `Breadcrumb`, no listing page above it) while keeping its own pre-existing two-column structure: a `flex flex-col md:flex-row` shell (owned by the page itself now, not a shared layout — see Components below) with a sticky `md:w-1/2` gallery column and a `md:w-1/2` content column that reorder via `order-1`/`order-2` between mobile (gallery first) and desktop (content first, gallery second). The booking engine uses its own flex-based collapsed/expanded layout within that content column, with a two-month calendar grid (`sm:grid-cols-2`, one month hidden on mobile) — untouched by this session's change.

## Elevation & Depth

Flat by default, in both registers. No `box-shadow` was found anywhere in the scanned components or `globals.css`; the codebase's own review flags hard offset shadows and kickers-as-invented-devices as things a craft floor would ban, and this build ships with none. Depth and separation are conveyed entirely through flat color blocking (cream card on gray ground, black borders on beige) and a single 1px border vocabulary (`border-foreground`, `border-black`, `border-gray-300`/`400`), never through shadow.

## Shapes

Square corners throughout: no `rounded-*` utility was found on any card, button, input, or dialog. `calendar-legend-swatch` even explicitly sets `rounded-none`. Borders are uniformly 1px solid, using `border-foreground`/`border-black` in the host register's form controls and calendar, and no border at all on catalog cards (separation comes from the cream-on-gray color block instead).

## Motion

Until this session, the build had exactly one authored animation (`expandDown`, the booking panel's collapse-to-expand entrance) and was otherwise instant everywhere — no transitions on hover, no feedback on press. The booking engine (both its canonical form at `/booking/[type]` and the identical shared components embedded in a blog post's `BookingWidget`) now carries one deliberate motion signature, added by explicit user direction ("overdrive the booking engine, turn it into a living material, but keep it as simple as shop is"): every interactive control gets the same physical press/release feel, and two controls additionally reveal their new state from the point of contact rather than snapping to it. Nothing else changed — no shadow, no gradient, no rounded corner was introduced to sell the effect; the physicality comes entirely from motion on the existing flat, square, color-blocked surfaces, which is what keeps it "as simple as shop."

**`--ease-spring`** (`cubic-bezier(0.34, 1.56, 0.64, 1)`, a `@theme inline` token, generating the `ease-spring` Tailwind utility): the one curve every motion below shares. A mild, deliberate overshoot — not a multi-oscillation bounce — chosen so a press reads as a physical object settling rather than a mechanical ease-out. (The mechanical detector flags any overshoot cubic-bezier as `bounce-easing`/"dated and tacky"; this is a known false positive against a confirmed, explicit user brief for a spring feel, not an oversight — see the Named Rule below.)

**Press/release (`press-spring` utility, `globals.css`):** every pressable control in the booking engine — calendar date cells, the room tabs, the collapsed date buttons, the Book/Close buttons, month nav, the person +/- steppers — compresses to `scale(0.97)` in a quick 60-100ms `ease-out` on press, then springs back to rest over 150ms on `ease-spring`. Declared as one multi-property `transition` (color, background-color, border-color, opacity, transform together) rather than composed from two separate utility classes, because a second class's own `transition` shorthand would silently replace the first instead of combining with it — this is why `press-spring` fully replaces `transition-colors`/`transition-opacity` wherever it's used rather than sitting alongside them.

**Sliding tab indicator (`TabIndicator.tsx`, shared by `RoomSwitcher`, `TabsDesktop`, `TabsMobile`):** the active room tab no longer swaps its own background instantly; a tan (`#d9b98b`, the same literal value the tabs always used — no new token) fill measures the active tab's real DOM rect and slides to it on `ease-spring` over 300ms. Works identically whether the active tab changes from client state (the blog widget's button toggle) or from an actual Next.js route navigation (`/booking/room1` ↔ `/booking/room2`), because both just re-render the indicator with a new `activeId` and it only cares which element currently carries that id. Caution for future edits: on `/booking/[type]` specifically (a route that streams via Cache Components), the sibling `<div ref={...}>` this component measures is not guaranteed to have its ref attached on `TabIndicator`'s first `useLayoutEffect` run — it read `null` there and only populated a frame or two later, a real bug caught during finish review (the indicator silently never appeared on the canonical booking page while working fine on the blog's plain static page). The effect now retries via `requestAnimationFrame` until the ref resolves rather than bailing out on that first null read; don't revert to a single-shot read assuming refs are always attached by first layout effect on every route in this app.

**Ripple-fill on calendar selection (`.calendar-date-selected`, `globals.css` + a click-coordinate handler in `BookingCalendar.tsx`):** a newly-selected date fills from the guest's actual click point via a `radial-gradient` with a hard color stop, its radius (`--ripple-r`, a `@property`-registered `<length>`) animating 0px → 80px on `ease-spring`. The click coordinates are written straight to the button's inline style at click time (not through React state — a one-shot presentational value, already on the DOM node before the class change that starts the transition), so a keyboard selection simply leaves them unset and the fill opens from center instead. Caution for future edits: `@property`'s `initial-value` means a bare `var(--ripple-r, 80px)` fallback never fires (the property is never "unset"); the target radius has to be explicitly declared on the class rule itself, not just referenced.

### Named Rules

**The One-Motion-Signature Rule.** Every animated thing in the booking engine draws from the same `--ease-spring` curve and the same press/release pattern; nothing gets its own bespoke easing or duration. This is a deliberate departure from the rest of the site's near-total absence of motion, confined to this one surface by explicit user request — don't extend spring easing to the catalog register's hover-underline or other unrelated interactions without the same kind of explicit direction.

## Components

### Buttons

- **Shape:** square corners, 1px solid border where a border exists (`px-4 py-2 border border-foreground`).
- **Primary (host register):** solid black fill, beige text (`bg-foreground text-background`), `hover:opacity-80`. Used for "Book" actions (`booking-book-button`, `booking-book-button-expanded`).
- **Secondary/Outline (shared, `.button-outline`):** black border and text, inverts to solid black on hover; the fill itself now diverges between its two consumers. Base rule is beige (`bg-background`), still what the shop wishlist trigger shows. The booking engine's own Close button (`.booking-close-button`) overrides that to white — a same-specificity, later-in-source-order rule, not a compound selector, so its position in `globals.css` matters: it must stay after `.button-outline` or the override silently stops working with no build error. See Pure White above for why.
- **Catalog text buttons:** uppercase, `tracking-[0.2em]`, `text-xs`, bordered on `current` color (wishlist dialog's Save/Close). No fill at rest.

### Cards / Containers

- **Corner Style:** square (no radius).
- **Background:** `bg-shop-card` (cream) for every catalog card and detail panel, including `/booking/[type]`'s own page shell now; the booking engine's own expanded panel is white (`bg-white`, see Pure White under Colors above) regardless of what it's embedded in, bordered rather than color-blocked.
- **Shadow Strategy:** none (see Elevation & Depth).
- **Border:** catalog cards have none; host-register panels/inputs use `border border-foreground`.
- **Internal Padding:** `p-3.5` on catalog cards; `p-4` on the expanded booking panel and wishlist dialog body.

### Inputs / Fields

- **Style:** square, 1px `border-foreground` (or `border-current` in the wishlist form), white or transparent background, `text-sm`.
- **Focus:** `outline outline-2 outline-foreground outline-offset-2` on calendar dates and the WhatsApp opt-in checkbox (host register); the wishlist email field instead shows a red border (`border-red-500`) plus inline text on validation error.
- **Error/Disabled:** disabled states drop to `opacity-30`–`opacity-50` with `cursor-not-allowed`; no other disabled treatment.

### Navigation

- `Header.tsx`: the wordmark link (handwritten face) appears only on non-home pages; nav items (Booking/Blog/Shop/Contact) are plain text links with a 2px black bottom border (`border-b-2 border-black`) marking the active section, no background pill or color change. `bg-white`, set apart from the page below it by `md:border-b md:border-gray-300` — chrome, not page content, so instead of trying to color-match whichever register the page below it belongs to, it's a third, explicitly white surface shared by both.
- `Footer.tsx`: same situation as Header, same white-plus-border device, applied the other direction. Rendered once per page in `(main)/layout.tsx`, `bg-white` regardless of register, marked off from the page above it with `border-t border-gray-300` (Header's own device, borrowed) at every breakpoint — not just `md:`, since the color break it's covering for is equally visible on mobile. See Layout above for why this, and not a register-aware background, is the fix. Its four pieces — the Instagram icon, "Terms & Conditions", "Privacy Policy", and the copyright line — sit in one `flex flex-row flex-wrap items-center justify-center` row (`gap-x-4 gap-y-1.5`) rather than the three stacked rows this used to be, with `py-3` replacing the old `pt-6 pb-4`: consolidating to a single row is what let the vertical padding shrink too, not just a reflow. `InstagramLink`'s own `mb-4` (a leftover from when it was the top of a vertical stack) was dropped along with it. `flex-wrap` is deliberate, not an accident of the row layout: at desktop width all four pieces read as one compact line, but at narrow mobile widths (~390px) the icon plus both legal links plus the full "© 2026 issebya.homes. All rights reserved." sentence don't fit one line, so the row wraps onto two, still centered, instead of forcing a single line to shrink or scroll. This is the same shared, single-instance, register-agnostic component described above — the row/wrap treatment applies identically regardless of which register's page precedes it.
- `Breadcrumb.tsx`: shared by shop and blog detail pages (and `/shop/sell`), `text-xs text-black` (changed from `text-gray-600` by explicit instruction — the parent link's own `hover:text-black` became redundant once the base color was already black, and was dropped rather than left as a no-op), underlined parent link (always, not hover-only — see Footer's own links below for the surface that _did_ move to hover-only), `›` separator marked `aria-hidden`, current item truncated to one line. Lives inside its page's own `bg-shop-card` panel now, as that panel's first child, not in a separate `px-4 pt-4` wrapper above it on the plain page background — it used to sit outside (a different, subtly mismatched color from the cream panel directly below it, the same category of seam Header/Footer had against their own adjacent pages), by explicit user instruction to make it "part of the page." `shop-card-edge-to-edge.browser.test.tsx` encodes this: it asserts `card.firstElementChild` is the breadcrumb `nav`, not that the nav sits above/outside the card (its earlier, opposite assertion, before this change).
- `Footer.tsx`'s "Terms & Conditions" and "Privacy Policy" links: underline on hover only, by explicit instruction — a real exception to `text-secondary-link` (the shared utility every other secondary link on the site uses, which underlines at rest). Written out directly at the two call sites (`text-secondary hover:underline underline-offset-4`) rather than added as a variant to the shared class or an override composed on top of it, since `text-secondary-link` has other consumers sitewide (`WhatsAppLink`, the location/reviews links on `/booking/[type]`, etc.) that were not asked to change and shouldn't silently pick up a different hover behavior.
- Room tabs ("Room 1"/"Room 2", `tab-styles.ts`'s shared `tabClasses()`): rendered uppercase ("ROOM 1"/"ROOM 2") by explicit instruction, a CSS `text-transform` on the shared class — the underlying label strings stay mixed case, and this applies identically everywhere the tabs render (`RoomSwitcher` on the blog widget, `TabsDesktop`/`TabsMobile` on `/booking/[type]`), since all three consume the same helper.

### Position-Marked Catalog Card (signature component)

The recurring, reused shop/blog card: whole-card `<Link>`, cream ground, uppercase kicker (brand name or formatted date), a title that underlines on `group-hover` only, and a 3-line-clamped description. `ProductCard` (shop) is portrait — photo filling the top 58% (`basis-[58%]`), text below — a centered kicker, a `text-price` (bold, `text-xl`) name. `PostCard` (blog) is horizontal instead — photo left (`w-2/5 sm:w-1/3`, `aspect-square`), text beside it in a single-column stacked list, not a grid — a left-aligned date kicker, a smaller and lighter `font-medium text-sm my-[10px]` title (by explicit instruction, not the shared `text-price` token). Only the hover-only underline behavior is shared identically between the two titles (an earlier, blog-only permanent underline was tried and reverted — see Catalog Title above); everything else about `PostCard`'s title and kicker — size, weight, alignment — was deliberately detuned from `ProductCard`'s to read as a distinct, quieter surface. A new catalog-register listing surface should reuse the shared ground/card/kicker tokens and the hover-underline convention; it does not have to reuse the portrait silhouette or `ProductCard`'s specific title size/weight/alignment — decide each deliberately, the way blog did.

Neither card carries a roman-numeral position marker any more, but they got there by different paths worth keeping straight. `PostCard` never had one: blog was built to mirror shop's grammar but diverged on this one point from the start, by explicit instruction, on the reasoning that a post isn't a numbered inventory item the way a product is. `ProductCard` _did_ have one (`toRoman(position)`, rendered above its kicker) for most of this session, since a product genuinely is a numbered catalog item — that reasoning held until a later, separate round removed it too, again by explicit instruction, with no reason given beyond the instruction itself. That round also deleted `toRoman`/`src/lib/shop/roman.ts` and its dedicated unit test outright, once grepping confirmed nothing else in the app called it — a genuinely orphaned utility, not a device kept in reserve. `ProductCard`'s `position` prop went with it (it existed only to feed `toRoman`), and `/shop/page.tsx`'s product `.map()` dropped the now-unused `index` it used to pass in as `position={index + 1}`. The net effect: `ProductCard` and `PostCard` are now closer to each other than they've been all session — cream ground, kicker, hover-underline title, no numeral on either — with the portrait-vs-horizontal silhouette and the title's size/weight/alignment left as the two decks' only remaining deliberate differences. Don't read the numeral's absence as an oversight or bring it back "for consistency" without asking; it was a considered removal on the one card that ever had it, not a gap.

### Inline Booking Widget (register crossover)

`BookingWidget.tsx` wraps the real `BookingEngine`/`BookingClient` (the same component `/booking/[type]` renders — calendar, date buttons, price, forms) in a catalog-register shell when embedded in a blog post: `bg-shop-card` panel, `border border-foreground` (added so the panel reads as its own object against the surrounding `bg-shop-card` prose — without an edge, a cream widget on a cream page visually merges), `max-w-xl`, `p-4 md:p-8`, left-aligned uppercase-tracked kicker "Book Your Stay" above the room tabs (left-aligned, not centered, to match the flush-left rhythm of the tabs/prose around it). This is one of two places the two registers deliberately meet (see the canonical page's own shell below) — only the outer shell crossed over to match the post around it. The engine's own internals were left alone through several rounds on the reasoning that restyling them would restyle the main booking page too (they are the same shared component, not a copy) — that reasoning now cuts the other way: its surfaces (date buttons, expanded panel, Close button) were explicitly changed to white this session, on the shared component itself, so both this widget and the canonical page picked up the change together, by design, not as a side effect. See Pure White under Colors above. The panel caps its own width at `max-w-xl` independent of the surrounding prose (which deliberately flows the post's full measure, see Layout above): the prose container's own lack of a `max-w` is about text reading fine at any width, but a booking form and calendar stretched to a full 1300px+ desktop measure reads as broken, not generous. Capping only the widget, not the prose around it, keeps the post's full-width text decision intact while bringing the form back to roughly the scale it has on its own `/booking/[type]` page (a `md:w-1/2` column).

### Booking Page Shell (register crossover)

`/booking/[type]/page.tsx` got the same wrapper treatment this session, applied to its own canonical page rather than an embedded copy: the page's `flex flex-col md:flex-row` shell (now owned directly by `page.tsx`, replacing the shared `booking/layout.tsx` that used to supply it for both this route and `/booking/confirmation`) sits on `bg-shop-card` instead of the beige `--background`. Inside it, the `TabsDesktop`/`TabsMobile` tab bar and the sticky `Gallery` column stayed untouched; the `BookingEngine` itself now shows white surfaces rather than beige ones — see Pure White under Colors and the Inline Booking Widget note above, since it's the identical shared-component change, not something specific to this page. Page-owned copy also changed: the closing enquiries line (now a plain `text-secondary` paragraph instead of the dashed-border `<Callout>`, the same substitution `/contact` made — see its own note above). The room title (`h2`, "Private room 1"/"Private room 2 with shared spaces") first moved to `text-price`, then was removed from the page entirely in a later round, by explicit instruction — the content column now runs straight from the tab bar into the collapsed booking engine. That same round joined what used to be two separate lines — this page's own `cap: max 2 persons` and `BookingPricing.tsx`'s `.booking-cancellation-notice` ("Once a reservation is made, we are unable to provide a refund", rendered inside the engine, shared with the blog widget) — into one `text-secondary text-xs` paragraph living entirely in `page.tsx`: "Capacity: max 2 persons. Once a reservation is made, we are unable to provide a refund." `.booking-cancellation-notice` was deleted from `globals.css` as part of that move (nothing referenced it anymore); `BookingPricing.tsx` now renders only the price. Because that notice used to live in the shared engine component, this is a real, disclosed behavior change beyond this page: the blog's Inline Booking Widget no longer shows a cancellation notice at all — only the price — since the merged capacity+notice line is page-owned copy that widget never had a counterpart for. A later, separate pass restyled one small piece of `Gallery` itself — its per-photo caption, now `text-xs font-medium uppercase` instead of the shared `text-secondary` body treatment — see Gallery Caption under Typography above; that change is presentational only (small/uppercase/medium-weight), doesn't move the caption or its container out of the host register, and `Gallery` has exactly one call site (this page), so nothing else was affected by it. The result is a cream page with a white, bordered booking panel sitting inside it — visually the same combination the Inline Booking Widget already ships, just at the scale of a full page instead of an embedded card. `/booking/confirmation` was deliberately left out of this pass: it now carries its own copy of the old shared beige/flex-row wrapper (`booking/confirmation/layout.tsx`) so its own page shell is byte-for-byte unchanged and stays host register per this file's Overview — though note it does still render the same `BookingEngine`-adjacent components' shared classes if it ever embeds the engine, so a future edit there would pick up the white surfaces too, by the same shared-component logic.

## Do's and Don'ts

### Do:

- **Do** keep `bg-shop-ground`/`bg-shop-card` and uppercase kickers confined to the catalog register (shop, blog, and now contact); a new catalog-adjacent listing page should reuse the Position-Marked Catalog Card's token set and grammar (not necessarily its portrait silhouette — see the signature component note above; neither card carries a roman numeral any more).
- **Do** treat `/contact` as catalog register now: `bg-shop-card` panel, `text-price` title, `text-secondary` body. It has no index of its own, so it borrows shop/blog's detail-page panel grammar (no `bg-shop-ground`, no `Breadcrumb`) rather than their listing-grid grammar.
- **Do** treat `/booking/[type]`'s own page shell as catalog register too, following the same pattern: `bg-shop-card` background, no `Breadcrumb`, no room-title heading (removed by explicit instruction — see Typography > Hierarchy and Booking Page Shell above). Its embedded `BookingEngine` keeps host-register styling for everything except color, which is now explicitly white by the same instruction that removed the title — see Pure White under Colors.
- **Do** keep the handwritten face (`font-hand`/`text-header`) confined to the host register's headline and wordmark; every other heading, including in-article MDX headings, stays bold Work Sans.
- **Do** keep corners square and surfaces flat (no radius, no shadow) in both registers.
- **Do** reuse `.button-outline` for any secondary action that needs to work in either register; it is already shared between booking's Close button and shop's wishlist trigger.
- **Do** treat a catalog-register wrapper around an unmodified host-register component (the Inline Booking Widget, and now `/booking/[type]`'s own shell) as a legitimate, narrow crossover when a host surface is embedded inside or wrapped by a catalog surface — don't restyle the embedded component itself to "finish the job."
- **Do** let genuinely shared, single-instance chrome (`Header.tsx`, `Footer.tsx`) stay `bg-white` and register-agnostic, marking its boundary with a plain `border-gray-300` hairline instead of trying to color-match whichever register the adjacent page happens to be in — see Layout above.
- **Do** put a page's `Breadcrumb` inside its own `bg-shop-card` panel, as the panel's first child, not in a separate wrapper above it — see Navigation above.

### Don't:

- **Don't** mix registers on one page (e.g. a cream catalog card with a handwritten heading, or a beige host panel with roman numerals). The build keeps them strictly separate.
- **Don't** introduce a drop shadow or rounded corner. Neither exists anywhere in the current build; both registers are flat and square by convention, not oversight.
- **Don't** add a bright/saturated accent color. Every hue in the shipped palette is desaturated (cream, gray, beige, black); a vivid accent has no precedent here.
