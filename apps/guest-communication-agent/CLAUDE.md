# GCA engineering conventions

## Tracing/durability plumbing

- Never hand-nest `step.run(id, () => withTurnSpan(...))`. Use `steppedSpan(step, id, traceAnchor, name, attrs, fn)` from `src/lib/tracing.ts` — collapses Inngest's step + this app's OTel span into one call.
- Every tool owns its own `gen_ai.tool.<name>` execution span and any `step`/`waitForEvent` usage it needs — created inside that tool's own `run<ToolName>`, per this app's `run<ToolName>` convention (`wants-human.ts`'s `runWantsHuman` is the model). `run-turn.ts`'s dispatch loop calls `run-tool.ts`'s `runTool` uniformly and does no span-wrapping of its own for any tool. Two tiers, differing only in HOW MUCH step/span machinery a tool needs, not in whether it needs any:
  - No real side effect worth protecting across a crash: wrap the whole thing in one `steppedSpan` call (`tool-execution.ts`'s `dispatchToolExecution` is the shared helper for this — `pricing.ts`'s `runGetPricing` is the model). The tool's actual business logic stays a separate, genuinely pure function (`compute<ToolName>`/similar) that the traced `run<ToolName>` wraps — keep that inner function pure even though the outer one isn't, especially if (like `pricing.ts`/`availability.ts`/`current-date.ts`) it's also called from a non-traced internal path (`run-code.ts`'s sandboxApi).
  - A real side effect that must not double-fire on an Inngest retry (an owner nudge), or a genuine suspend/wait (`waitForEvent`) — needs its own, finer-grained `step.run` calls beyond one `steppedSpan`. `wants-human.ts`'s `runWantsHuman`, `missing-info.ts`'s `requestMissingInfoApproval`, and `booking.ts`'s `requestSendBookingLinkApproval` are the model. `missing_info`/`send_booking_link` additionally split their approval half (`request<ToolName>Approval`) from their execution half (`runMissingInfo`/`runSendBookingLink`) because the approval wait can suspend for up to a year — no single tool call can own a span spanning that. The two halves own two DIFFERENT spans, not one shared span: `request<ToolName>Approval` creates its own `hitl.<name>` GATE span up front (before the wait starts, so nudge/decision/timeout spans nest under it), and patches ONLY that span with the not-approved outcome if the call is rejected/times out — it never creates or touches the real `gen_ai.tool.<name>` execution span. `run<ToolName>` is only ever called once approved, and creates that execution span completely fresh at that point (the exact same one-shot `steppedSpan`/`dispatchToolExecution` shape every plain tool already has, real output known at creation — no pre-created span, no `toolSpanId` param, no retroactive patch). Nesting the approval wait under a span literally named "the tool call" would misrepresent the sequence (approve, THEN call the tool) as happening inside the tool call — that's exactly the bug this two-span split fixes; see `missing-info.ts`'s/`booking.ts`'s own comments. `run-turn.ts`'s dispatch loop is what drives this: its `NEEDS_APPROVAL` set and the inline switch over `request<ToolName>Approval` calls (deliberately not its own named function — this is the one place that needs to know "how do I get a decision for tool X") live directly in that file, not a separate module.
  - `property-question.ts`'s own inner `db.matchDocuments` span and `owner-nudge.ts`'s send span are a narrower, older kind of exception (a plain OTel span nested inside the tool's own execution span, zero step/Inngest coupling) — not durability plumbing, just finer-grained tracing.
  - If you're adding a new tool, ask which tier it's in before writing its dispatch — don't default to the heavier one.
- Inside a `steppedSpan`/`withTurnSpan`/`withSpan` call, pass a named function for any real logic — not a trivial one-liner — declared just above the call, closing over the same locals. Keeps the wrapper call itself scannable as pure plumbing, separate from the logic.

## Comments

- Only comment genuine landmines: a non-obvious constraint that breaks something if the reader doesn't know it (Inngest's step-nesting rule, its required-bounded-timeout rule, Braintrust's attribute-to-UI mapping, Twilio's raw-body signature requirement). State each such fact once, at its canonical definition (e.g. `steppedSpan`'s doc comment, the "RULE" comment near the top of `run-turn.ts`) — reference it tersely from other call sites instead of re-explaining it each time.
- Don't write narrative/changelog-shaped comments ("as of DATE, X replaced Y because Z", "previously this did A, now it does B"). That belongs in the commit message. If a narrative comment contains a real fact worth keeping, state the fact plainly and drop the history wrapped around it.
